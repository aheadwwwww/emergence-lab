# Agent 记忆生命周期系统 v1

> 从研究中学到的核心结论：记忆不是静态存储，是一个处理管线。
> 参考：Agent-Native Memory (ByteRover, 2026), Oracle Agent Memory, 认知心理学

---

## 整体架构

```
输入 → CAPTURE → CURATE → CONSOLIDATE → ACTIVATE → REVIEW
                         ↓                          ↑
                    FORGET/ARCHIVE ← ← ← ← ← ← ← ← ←
```

### 五个阶段

| 阶段 | 做什么 | 当前状态 | 问题 |
|------|--------|---------|------|
| 🎯 CAPTURE | 捕捉教训、经验、反馈 | ✅ 有（lessons.md） | 无标准，凭感觉 |
| 🔍 CURATE | 筛选：这个值得记吗？ | ❌ 缺失 | 什么都记=什么都不记 |
| 🔗 CONSOLIDATE | 合成：多个教训→一个原则 | ❌ 缺失 | 教训之间无关联 |
| ⚡ ACTIVATE | 在决策时刻介入 | ❌ 缺失 | 核心断裂点 |
| 🔄 REVIEW | 验证：行为真的变了？ | ❌ 缺失 | 无法判断迭代是否有效 |

---

## 阶段一：CAPTURE（捕捉规则）

### 什么该记？

只有通过以下 **三条过滤** 的东西才值得写进教训系统：

```
1. 它能改变我的下一次决策吗？       → 是 → 通过
2. 它有可识别的触发场景吗？        → 是 → 通过
3. 我能验证它生效了吗？           → 是 → 通过
```

不通过任意一条 → 记入「临时草稿」但不进入激活系统。

### 记录格式（单条教训）

```yaml
TRIGGER: <3-5词描述触发场景>
RULE: <一句话，可执行>
VERIFY: <如何验证做到了>
SEVERITY: RED|YELLOW|GREEN  # 对应 lessons.md 的三级
SOURCES: <可选，来自哪次教训>
VERSION: <版本号>
```

示例：
```yaml
TRIGGER: 声明"完成/已修复"
RULE: 必须做三合一验证（存在+执行+可验证）
VERIFY: 检查最终输出是否包含验证结果
SEVERITY: RED
VERSION: 1
```

## 阶段二：CURATE（筛选规则）

### 过滤条件

每次会话结束时，快速跑一次 curator。

#### 追踪方法
在 `memory/lesson-activation-log.md` 中记录每次激活情况：
```
格式：YYYY-MM-DD | 教训ID | 激活(是/否) | 执行(是/否) | 验证(是/否)
```

#### 过滤逻辑
```
待筛选条目检查：
  这条教训在今天被激活了吗？  → 否 → 在激活日志中写「否」
  这条教训改变了我的行为吗？  → 否 → 标记为「未激活」
  这条教训是否重复？        → 是 → 合并到同类原则
  连续3次会话未激活 → 降级到「观察区」（在lessons.md中移出RED/YELLOW）
  连续10次会话未激活 → 归档到 `memory/archived-lessons.md`
```

### 存档机制

```
激活系统（活跃教训，上限15条） ← lessons.md 中的 RED+YELLOW
    ↑ 升级（被激活+验证有效≥2次）
观察区（待确认教训，上限30条） ← lessons.md 末尾的 OBSERVE 节
    ↑ 晋升（第一次捕获时）
临时草稿（新教训，每次会话后清空或晋升）← 空间记忆，不落文件
```

## 阶段三：CONSOLIDATE（合成规则）

### 从教训到原则

多条教训如果有共同的根模式 → 合成为一个原则。

示例：
```
教训 1: 声明"修复"→没验证→虚假闭环
教训 2: 改了三处→只验证了第一处→另外两处炸了
     ↓ 合成
原则: 任何"完成"声明必须通过三合一验证（存在+执行+可验证）
```

### 冲突检测

新教训与现有原则冲突 → 要么合并，要么升级为旧版无效。

---

## 阶段四：ACTIVATE（激活规则）⭐ 最关键的环节

### 激活机制设计

**问题**：教训在上下文里，但决策时不去查。
**解决**：把激活从「被动查询」改为「主动匹配」。

```
每次我准备做一次行动（回复/修改/建文件/自选任务），
自动过一遍激活检查：
```

**激活步骤：**

```
1. 当前场景匹配 → 列出所有TRIGGER匹配的教训
2. 执行匹配教训 → 遵循RULE
3. 检查输出 → 通过VERIFY标准
```

### 场景匹配表（行动类型 → 检查哪些教训）

| 行动类型 | 自动匹配的TRIGGER | 检查项数 |
|---------|-----------------|---------|
| 回复用户消息 | "漏消息""多问题""声明完成" | 3 |
| 构建/改代码 | "完成/已修复""过度设计""发烫bug" | 3 |
| 自选任务 | "自己做事""惯性""值得做吗" | 3 |
| 失败恢复 | "连续失败""子任务超时" | 2 |
| 告诉用户"好了" | "声明完成""虚假闭环" | 2 |

### 紧急激活（RED 级）

RED 级别的教训（红线级）必须在每次回复前强制检查，不跳过的。

---

## 阶段五：REVIEW（验证规则）

### 会话结束后验证

```
□ 这次会话有没有违反任何教训？
□ 如果有 → 在当天的日记里记录
□ 有没有教训被激活但没执行？
□ 有没有教训本应被激活但没出现？
```

### 定期审计

- **每周**：curation（清理未激活教训）
- **每月**：consolidation（检查是否有原则需要合并或废弃）
- **每季**：回头看—判断力是否在增长

### 判断力斜率（核心指标）

```
不是「我记了多少」，
是「我的判断力斜率是多少」——每次做决定比以前更好吗？
```

## 附录：认知科学原理参考

| 原理 | 应用到我的系统 |
|------|-------------|
| 遗忘曲线 (Ebbinghaus) | 不定期激活的教训会自动降级 |
| 间隔重复 (Spacing Effect) | 活跃教训需要不同场景下的重复激活 |
| 检索练习 (Retrieval Practice) | 每次激活=主动检索，强化记忆 |
| 编码特异性 (Encoding Specificity) | TRIGGER 匹配 = 编码-检索匹配 |
| 记忆巩固 (Consolidation) | 从教训到原则的合成过程 |
| 测试效应 (Testing Effect) | VERIFY 验证 = 测试，强化行为改变 |
